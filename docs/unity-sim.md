# 仿真环境：Unity WidowX 闭环

本文记录把 X-VLA（WidowX 版）接进 Unity 仿真里跑闭环的过程、接口契约与踩坑点。
目标是让「模型出动作 → 机械臂在场景里动」这条链路可复现，不追求仿真里的任务成功率。

## 1. 架构

```
Unity 独立播放器（WidowX-250 场景）
   │  TCP 127.0.0.1:7777  行协议
   ▼
Python 闭环脚本
   ├─ transformers + X-VLA-WidowX（PyTorch，CPU/CUDA）
   ├─ 实测雅可比（位置 3×6 / 旋转 3×6）
   └─ 关节增量下发
```

- Unity 侧只负责「观测出图 + 关节跟随」，不含任何控制逻辑。
- 闭环频率由 Python 决定：动作回放 10 Hz，每 2 个 tick 更新一次目标。
- 独立播放器（不是编辑器 Play Mode）是刻意选择，原因见 §6。

### 2.2 URDF 导入要点

1. **网格格式**：Unity 的 URDF Importer 对 `.obj` 走 `AssetDatabase` 查找，路径解析容易失败；改用 `.stl` 后由 `StlAssetPostProcessor` 生成带 MeshFilter 的 prefab，稳定。URDF 里保留 `scale="0.001 0.001 0.001"`（STL 单位是毫米）。
2. **`chosenAxis` 用 `yAxis`**：用 `zAxis` 会把整条臂拆散（网格与关节原点对不上）。
3. **驱动单位**：`ArticulationDrive.target`（转动关节）是**度**，`jointPosition` 是**弧度**。按弧度下发 → 关节几乎不动，整条臂在重力下塌下去，表现为「站不稳」。
4. **根节点**：`base_link` 必须 `immovable = true`（`useGravity = false`），否则整条臂是自由刚体，会倾倒。
5. **`Controller` 组件**：URDF Importer 自带的 `Controller` 每帧写 `xDrive`（给运行时滑条用），会和外部控制打架，必须禁用。
6. 关节限位来自 URDF（例：`shoulder [-108°, 114°]`、`elbow [-123°, 92°]`、`wrist_angle [-100°, 123°]`），控制侧要在限位内裁切。

## 3. 桥协议（TCP 7777）

一行一条命令，返回一行 JSON。

| 命令 | 返回 | 说明 |
| --- | --- | --- |
| `OBS` | `{joints[6], grip, ee[3], ee_quat[4], images[2]}` | 关节（弧度）、夹爪开度、末端位姿（相对机器人根节点）、两路 224×224 PNG（base64） |
| `STATE` | `{joints, grip, ee, ee_quat}` | 同上但不带图，供 20 Hz 伺服使用 |
| `ACT q0..q5 grip` | `{ok:true}` | 关节目标（弧度）+ 夹爪 0..1（1 = 闭合） |
| `READY` | `{ok:true}` | 回到预设位姿 |
| `INFO` | 关节名/类型/限位/驱动参数 | 调试用 |

`ee` 与 `ee_quat` 是 `gripper_link` 在机器人根坐标系下的位姿。

## 4. 模型侧约定

依据官方评测客户端 `2toINF/X-VLA` → `evaluation/simpler/WidowX/client_blocks.py`（**不要自己猜**）：

- 输入：单张 224×224 图（我们传 2 视角，processor 会把第 3 槽补零、`image_mask` 标 False）
- `proprio`（20 维）：`[ee_pos(3), 1,0,0,1,0,0,0]`，其余补零；**不含夹爪**
- 动作（30×20）：`action[:3]` 是**绝对**末端位置，`action[3:9]` 是 6D 旋转，`action[9]` 是夹爪概率
- 夹爪：`1.0 if pred[9] < 0.91 else -1.0`（+1 = 闭合），**不是**直接取概率
- `steps=10`、`domain_id=0`
- 旋转：6D → 旋转矩阵 → 欧拉 `xyz`，再 `+[0, π/2, 0]`

坐标系的结论：`proprio` 喂哪个系的末端位置，模型输出的位置就在同一个系里，所以**不要**对位置做轴置换（早期版本把 `(x,y,z)` 换成 `(x,z,-y)`，表现就是「运动方向反了」）。

训练数据只有桌面相机，所以闭环默认**只喂 `cam_front`**（`XVLA_VIEWS=1`，可用环境变量改回 2）；腕部相机仍然渲染，只用于 HUD 预览，不进模型。

## 5. 控制栈

模型给的是末端位姿，Unity 吃的是关节角，中间是 IK。这里**不用 URDF 解析解**，而是在运行中的场景里测雅可比：

1. 每个 chunk 开始时，把 6 个关节各加 0.06 rad，用 `STATE` 记录末端位置与姿态变化，得到 `J_pos`（3×6）和 `J_rot`（3×6）。
2. 位置：全臂 3×6 阻尼最小二乘，单 tick 关节增量上限 0.08 rad，目标相对当前位置限幅 ±8 cm 且不低于台面 3 cm。
3. 姿态：只用腕部三关节（`forearm_roll` / `wrist_angle` / `wrist_rotate`）的 3×3 子块求解，单 tick 上限 0.12 rad；机械臂还在赶路（位置误差 > 2 cm）时腕部保持不动，避免两段控制互相拉扯。
4. 死区：位置误差 < 4 mm 且姿态误差 < 0.02 rad 时保持不动，避免把模型输出的采样噪声放大成抖动。
5. 旋转目标按 **chunk 内相对量** 使用：`R_target(k) = R_start · (R_pred(k) · R_pred(0)ᵀ)`，把预测之间的旋转变化叠到当前姿态上，模型与场景之间的常数坐标系偏差可以抵消。
6. 旋转增量按 0.30 rad 裁切；关节限位留 2° 余量（驱动会过冲）。

实测（CPU，4 个 chunk）：位置跟踪误差 ≤ 3 mm；静止时关节抖动为 0（见 §7）。

## 6. 为什么不用编辑器 Play Mode

通过 MCP 触发 `manage_editor play` 后，Unity 主线程会卡住（MCP 命令全部超时、编辑器无响应），需要重启编辑器。改用独立播放器后没有这个问题，而且播放器不依赖编辑器 UI，适合跑长实验。

## 7. 实测数据

主机：RTX 5060 Laptop（当前 torch 为 CPU 版），16 线程。

| 项目 | 数值 |
| --- | --- |
| 模型加载 | 20.5 s |
| 推理（steps=10，30×20 动作块，CPU） | 7.1–9.1 s（≈0.12 Hz） |
| 位置伺服跟踪误差 | ≤ 3 mm |
| 单 chunk 执行 | 30 动作 × 2 tick @ 20 Hz ≈ 3 s |
| 静止时关节抖动 | 20 次采样标准差 0.000°（死区生效） |

采样噪声探针（同一帧观测，各跑一次）：

| 条件 | 首个动作 xyz | 夹爪 |
| --- | --- | --- |
| `pick up the red block`，2 视角 | `[0.313 0.061 0.089]` | 0.010 |
| 同上，重复 | `[0.314 0.051 0.090]` | 0.001 |
| `pick up the red cube`，2 视角 | `[0.313 0.064 0.092]` | 0.007 |
| `pick up the red block`，1 视角 | `[0.312 0.053 0.087]` | 0.005 |

结论：模型对不同指令、不同视角数的输出几乎不变，首个动作贴着当前末端位置（`[0.307 0.061 0.095]`）——本场景下它倾向「原地不动、保持张开」。这是分布外（OOD）的直接证据：X-VLA-WidowX 只在 Bridge / SimplerEnv 数据上训练，我们的桌面、光照、物体都不在分布内。

末端到方块的直线距离（4 个 chunk，方块在 `(0.26, 0.02, 0.34)`）：

```
0.297 → 0.268 → 0.269 → 0.283
```

末端在 x/y 上朝方块移动，但没有收敛到方块（最终 `ee ≈ (0.334, 0.030, 0.068)`，z 差约 27 cm）。可以观察到「有意图但落点不对」的行为，这与 OOD 的预期一致。

视角消融（同样从 READY 位姿出发，方块 `(0.26, 0.02, 0.34)`）：

| 输入视角 | 每 chunk 后到方块距离 | 编码器耗时 |
| --- | --- | --- |
| 2 视角（桌面 + 腕部） | 0.297 → 0.268 → 0.269 → 0.283 | ≈1.9 s |
| 1 视角（仅桌面，训练同构） | 0.317 → 0.286 → 0.282 | ≈1.0–1.35 s |

两者最终都停在 0.27–0.28 m 的平台，末端同样在 x/y 上靠近、z 差约 0.28 m。去噪初值每次随机，1.3 cm 的差异在噪声范围内，**看不出腕部视角有正贡献**；但省下了约 0.6–0.9 s 的编码器时间。结论：现阶段瓶颈不在视角数量，而在分布差异。

### 7.2 对齐训练集的两次尝试

参考帧取自官方模型卡的演示视频（`2toINF/X-VLA-0.9B-WidowX` 的 `demo.mp4`）：青绿色桌垫、浅色背景、机位在机械臂前上方约 40° 俯视。

| 设置 | 到方块距离（逐 chunk） | 说明 |
| --- | --- | --- |
| 基线（Unity 坐标系、旧场景） | 0.297 → 0.268 → 0.269 | 见 §7 |
| 坐标系对齐 | 0.281 → 0.321 → 0.350 | `proprio` 转 ROS 系（`x, -z, y`），目标再转回 Unity；模型侧数学上自洽，但结果更差 |
| 坐标 + 视觉对齐 | 0.318 → 0.280 → 0.313 | 桌垫改成采样自参考帧的青绿色、机位拉近到前上方 40°、背景调亮 |

结论：两种对齐都没有把落点拉回方块，差异都在随机性范围内。更有诊断价值的是首个动作——每次推理的第 0 步目标与当前末端距离只有 2–3 cm，也就是模型在本场景里仍然倾向「先按兵不动」，之后的位移是 chunk 内逐步累积出来的。这说明瓶颈不是坐标系或配色，而是策略没有把「红色方块」与这个场景里的物体对应起来。

要真正验证任务能力，得用训练分布内的评测环境（SimplerEnv + ManiSkill，需要 Python 3.9–3.10 独立环境），或者在本场景上做微调；在 Unity 里继续调外观收益有限。

推理过程中「推理」行会实时走条：`[==========--------] 55%  去噪 5/10`，`耗时` 行给出已用/剩余，`过程` 行给编码器耗时、当前步耗时和最近三步，方便判断是编码器慢还是去噪步慢。底部两张缩略图直接画的是相机的 RenderTexture（与 Python 侧编码成 PNG 的是同一份像素），不需要额外传输。

各字段来源：

| 行 | 来源 |
| --- | --- |
| 框架 / 流匹配步数 | Python 上报（`pytorch-<device>`、`steps`） |
| 推理条 / 阶段 / 步数 | 闭环脚本按 `forward_vlm` → 10 次 `transformer` → `postprocess` 逐段上报 `progress/stage/step` |
| 过程 / 耗时 | 编码器毫秒、单步毫秒（含最近三步）、已用与 ETA |
| 指令 / Token | 送给 processor 的文本指令（空格在协议里转成 `_`，显示时还原）与前 8 个 token id（`0`=BOS，`2`=EOS，`1`=pad） |
| 输入 / 缩略图 | 视角数、分辨率、文本 token 数、推理设备；两路相机 RenderTexture |
| 输入 | 视角数、分辨率、文本 token 数、推理设备 |
| 本次 | 本次推理拆解：`enc + 10×步 + post` |
| chunk 耗时 | 从开始推理到当前动作的墙钟时间（推理 + 30 动作回放） |
| 通信 | 最近若干次 `STATE` 往返的指数滑动平均 |
| 模型输出 / 姿态误差 | 当前动作的末端目标、夹爪、姿态残差 |
| 关节 / 目标 / 末端 | Unity 实时读取（弧度转角度） |
| 渲染 / 已执行动作 | Unity 帧率与 `ACT` 计数 |

进度上报是把 `model.generate_actions` 拆开重写的（encoder / 去噪循环 / 后处理），数学与官方实现一致，只是多了埋点；GPU 上同样可用，`设备` 会显示显卡型号。

## 8. 已知问题

1. **分布外**：仿真里的抓取成功率不能作为模型指标；链路通不等于任务成。
2. **旋转是相对量**：绝对朝向约定未验证，目前用 chunk 内相对旋转；绝对模式需要先校准模型到场景的旋转基准。
3. **夹爪只有二值**：按官方阈值离散成开/合，没有做开合度平滑。
4. **IK 依赖实测雅可比**：每个 chunk 重测一次（≈2 s），快速运动时线性化会失真。
5. **腕部会顶限位**：姿态需求大时 `wrist_angle` 会贴到 -96° 附近（限位 -100°），需要更强的姿态优先级或工作空间约束。
6. 脚本目前放在仓库外（原型），若要入库需要按 `docs/` 与 `scripts/` 规范拆分并补测试。
